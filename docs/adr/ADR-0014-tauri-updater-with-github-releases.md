# ADR-0014: Use Tauri Updater Plugin with GitHub Releases

**Date:** 2026-04-07
**Status:** Proposed
**Related:** PRD-0013 (Non-Intrusive Install Tracking and Usage Analytics)

---

## Context

openEHR Explorer is distributed via GitHub Releases with platform-specific installers (.dmg, .deb, .AppImage, .exe). Users must manually check for and download new versions — there is no in-app update mechanism.

This creates two problems:

1. **Version fragmentation:** Users stay on outdated versions indefinitely, requiring long-tail support and making it harder to deprecate old behavior.
2. **No install visibility:** GitHub download counts are the only adoption metric, and they don't distinguish downloads from actual installs or show which versions are actively used.

Tauri 2 provides an official updater plugin (`tauri-plugin-updater`) that supports checking for updates against a JSON endpoint and applying them in-place. GitHub Releases can serve as this endpoint with no additional infrastructure.

---

## Decision

We will **integrate `tauri-plugin-updater` with GitHub Releases as the update backend** for automatic update checking and installation.

### Configuration

**Tauri config (`tauri.conf.json`):**

```json
{
  "plugins": {
    "updater": {
      "endpoints": [
        "https://github.com/platzhersh/openehr-explorer/releases/latest/download/latest.json"
      ],
      "pubkey": "<public key generated by tauri signer>"
    }
  }
}
```

The `latest.json` file is a static JSON manifest generated during CI and uploaded as a release asset. It contains download URLs and signatures for each platform.

**Update check flow:**

```
App Launch
  → GET latest.json from GitHub Releases
  → Compare version in manifest vs current app version
  → If newer: show non-intrusive notification bar
  → User clicks "Update" → download + verify signature + install
  → Restart into new version
```

### Frontend Integration

A lightweight `UpdateNotification.vue` component checks on launch:

```typescript
import { check } from '@tauri-apps/plugin-updater';

const update = await check();
if (update?.available) {
  // Show notification bar with version info and "Update" button
  // User can dismiss — never block the UI
}
```

### CI Changes

The existing GitHub Actions workflow needs to:

1. Generate a Tauri signing key pair (one-time setup, stored as repository secret)
2. Build with updater support enabled (produces `.sig` signature files alongside installers)
3. Generate and upload `latest.json` manifest as a release asset

### Why GitHub Releases (not a custom server)

- **Zero infrastructure:** No server to deploy, maintain, or pay for
- **Already in use:** Releases are already published via CI on version tags
- **Built-in CDN:** GitHub's CDN handles download bandwidth globally
- **Transparent:** Users can verify what's being served by visiting the releases page
- **Upgradeable:** Can later switch the endpoint to a proxy (PRD-0013 Tier 2) without changing the app — just update the URL in `tauri.conf.json`

---

## Consequences

### Positive

- Users receive update notifications automatically on app launch
- Version fragmentation is reduced as users can update in one click
- Update checks provide a natural, non-intrusive "ping" that reveals active install counts (via download counts on `latest.json` and update assets)
- No additional infrastructure or ongoing costs
- Code signing via Tauri's built-in signature verification prevents tampered updates

### Negative

- **GitHub rate limits:** Unauthenticated API requests are limited to 60/hour per IP. For a desktop app checking once per launch, this is unlikely to be a problem in practice. Can be mitigated later with a caching proxy (Tier 2).
- **No detailed tracking from GitHub alone:** GitHub only shows total download counts, not unique users or platform breakdown from update checks. This is acceptable for Tier 1; Tier 2 (proxy) addresses it.
- **Signing key management:** A Tauri signing key pair must be generated and stored securely as a GitHub Actions secret. Loss of the private key would require all users to manually reinstall.
- **Update latency:** GitHub's CDN may take a few minutes to propagate new release assets globally.

### Neutral

- The updater adds ~50KB to the binary size (the plugin is lightweight)
- Update checks require network access; offline launches work normally (check silently fails)
- macOS and Windows may show OS-level permission prompts during the update installation process

---

## Alternatives Considered

1. **Custom update server (e.g., Cloudflare Worker from the start):** More control and tracking, but adds infrastructure complexity before we know the scale. GitHub Releases is simpler for Tier 1; the endpoint URL can be swapped later.

2. **Sparkle (macOS) / WinSparkle (Windows):** Mature update frameworks, but platform-specific. Tauri's updater is cross-platform and integrated into the build toolchain we already use.

3. **No auto-updater (manual downloads only):** Status quo. Provides no install visibility and creates version fragmentation. Users of desktop tools expect auto-update in 2026.

4. **Electron-style `autoUpdater` via Electron migration:** Would require rewriting the app. Tauri's native updater achieves the same result within our existing stack.
