# ADR-0013: Normalise OPT Term Binding Codes Before Use

**Date:** 2026-04-05
**Status:** Accepted
**Related:** PRD-0012 (Terminology Awareness in Template Browser and Composition Viewer)

---

## Context

During implementation of PRD-0012 (Terminology Awareness), we discovered that OPT files generated by Ocean Template Designer and similar tools serialise `CODE_PHRASE` values in ODIN bracket notation rather than bare concept IDs.

**Observed formats in the wild:**

- `[SNOMED-CT(2003)::364090009]` — Ocean TD legacy, version qualified
- `[SNOMED-CT::364090009]` — Ocean TD, no version qualifier
- `364090009` — bare code (some tooling, manual edits)
- `http://snomed.info/sct/364090009` — URI format (rare, seen in some Better Platform exports)

The bracket notation embeds three pieces of information in a single string:
1. Terminology ID (e.g. `SNOMED-CT`)
2. Optional version/release qualifier (e.g. `(2003)`)
3. Concept code (e.g. `364090009`)

When term binding codes in this format are passed raw to the FHIR `$lookup` endpoint, the entire bracket expression is sent as the `code` parameter, resulting in 404 responses. This issue was discovered when testing with Cistec's own clinical templates, making it a critical production concern rather than a theoretical edge case.

**Example failure:**
```
GET /ValueSet/$lookup?system=http://snomed.info/sct&code=[SNOMED-CT(2003)::364090009]
→ 404 (code not found)
```

**Expected behaviour:**
```
GET /ValueSet/$lookup?system=http://snomed.info/sct&code=364090009
→ 200 OK { display: "Finding of oxygen saturation", ... }
```

---

## Decision

We will **normalise all term binding codes at parse time** in the Rust OPT parser (`src-tauri/src/commands/template.rs`), before any code leaves the backend.

### Implementation

Add a `normalise_term_code()` helper function that:

1. Strips outer brackets `[...]` if present
2. Splits on `::` to separate terminology ID from code
3. Removes any version qualifier from the terminology ID (e.g. `SNOMED-CT(2003)` → `SNOMED-CT`)
4. Returns a clean `(terminology_id, code)` tuple

**Rust implementation:**

```rust
/// Normalise term binding codes from OPT format to clean (terminology_id, code) pairs.
///
/// Handles:
/// - `[SNOMED-CT(2003)::364090009]` → `("SNOMED-CT", "364090009")`
/// - `[SNOMED-CT::364090009]` → `("SNOMED-CT", "364090009")`
/// - `364090009` → `("", "364090009")` (bare code, no terminology ID)
fn normalise_term_code(raw: &str) -> (&str, &str) {
    let stripped = raw.trim_start_matches('[').trim_end_matches(']');

    if let Some((terminology_part, code)) = stripped.split_once("::") {
        // Remove version qualifier: SNOMED-CT(2003) → SNOMED-CT
        let terminology_id = terminology_part
            .split('(')
            .next()
            .unwrap_or(terminology_part);
        (terminology_id, code)
    } else {
        // No delimiter → bare code
        ("", stripped)
    }
}
```

This normalisation happens **once** when parsing `<term_bindings>` from the OPT XML. The rest of the application — terminology lookup, the Bound Concepts panel in the Template Browser, composition viewer code resolution — always receives clean `(terminology_id, code)` pairs and never needs to know what format the OPT originally used.

---

## Consequences

### Positive

- **Terminology lookup works correctly** for Ocean Template Designer–generated OPTs, including Cistec's production templates
- **Single normalisation point** in the parser; no defensive handling scattered across the codebase
- **Simpler downstream logic** — components can assume codes are already clean
- **Consistent developer experience** — Template Browser and Composition Viewer display normalised codes in Request Inspector

### Negative

- **Version information discarded** — OPT release qualifiers like `(2003)` are intentionally dropped. This is acceptable because:
  - FHIR terminology servers (`tx.fhir.ch`, Snowstorm Lite) resolve against their loaded SNOMED CT release, ignoring the qualifier
  - The OPT version qualifier is metadata about the *authoring environment*, not a runtime constraint
  - No known openEHR implementation enforces version-specific code validation at composition commit time

### Neutral

- **Must be tested against multiple formats** — unit tests should cover at least:
  - Bare code: `364090009`
  - Versioned bracket notation: `[SNOMED-CT(2003)::364090009]`
  - Unversioned bracket notation: `[SNOMED-CT::364090009]`
  - URI format (future): `http://snomed.info/sct/364090009` (not yet supported, but worth documenting for future enhancement)

---

## Alternatives Considered

### 1. Normalise at lookup time (Vue frontend)

**Rejected:** Would require duplicating normalisation logic in `src/lib/terminology.ts` and any other component that handles codes. Error-prone and harder to test.

### 2. Normalise in the Tauri `lookup_code` command

**Rejected:** The Bound Concepts panel in the Template Browser displays codes parsed from the OPT; it doesn't call `lookup_code` but still needs clean codes. Normalising only at lookup time would leave the Template Browser showing raw bracket notation.

### 3. Support version-specific lookup

**Rejected:** Would require mapping OPT version qualifiers to FHIR `version` or `system|version` parameters. No known terminology server used by openEHR deployments supports this, and the OPT spec doesn't mandate it.

## Testing Strategy

Add Rust unit tests in `src-tauri/src/commands/template.rs`:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_normalise_term_code() {
        assert_eq!(normalise_term_code("364090009"), ("", "364090009"));
        assert_eq!(normalise_term_code("[SNOMED-CT::364090009]"), ("SNOMED-CT", "364090009"));
        assert_eq!(normalise_term_code("[SNOMED-CT(2003)::364090009]"), ("SNOMED-CT", "364090009"));
        assert_eq!(normalise_term_code("[LOINC::8867-4]"), ("LOINC", "8867-4"));
    }
}
```

Integration test: Upload an Ocean TD–generated OPT with bracketed term bindings (e.g. Cistec's allergy template), verify the Bound Concepts panel displays clean codes and terminology lookup succeeds.
