Regenerate marketing assets for `$1` (default: both screenshots and video).

## Background

`docs/assets/screenshots/*.webp`, `docs/assets/demo.mp4`, `docs/assets/demo.gif`,
and `docs/assets/demo.vtt` are all generated by `scripts/demo-assets/`, not
hand-captured. There's no real EHRBase server and no native Tauri shell
involved: the toolkit drives the actual Vue frontend (`npm run dev`) in
headless Chromium via Playwright, with `scripts/demo-assets/mock.js`
stubbing `window.__TAURI_INTERNALS__.invoke` — the same boundary
`@tauri-apps/api/core`'s `invoke()` calls through — so every `invoke("cmd",
args)` call in the app resolves to realistic canned fixture data instead of
hitting a Rust backend.

This matters because it's why the EHR IDs (`9c2c5c5e-1c1b-...`), clinician
names (`Dr. A. Kessler`, `Dr. R. Okafor`), and the "Vital Signs" template
structure are identical across every screenshot, the hero video, and the
README gif — they're all reading from the one fixture module
(`scripts/demo-assets/mock.js`), not independently faked per asset. If you
need to change what the demo data looks like, edit fixtures there once;
don't hand-edit individual screenshots or hand-tune per-script data.

Full details, known limitations, and the file-by-file breakdown live in
`scripts/demo-assets/README.md` — read that first if this is your first
time touching this toolkit.

## Prerequisites

1. `npm install` (installs the pinned `playwright` devDependency).
2. `npx playwright install chromium` once, if Chromium isn't already
   present for Playwright in this environment.
3. `ffmpeg` and `gifsicle` on `PATH` — system packages (`apt install ffmpeg
   gifsicle` / `brew install ffmpeg gifsicle`), not npm packages.
4. A running dev server: `npm run dev` (default `http://localhost:5173`).
   Keep it running in the background for the whole regeneration.

## Step 1: Screenshots (if `$1` is `screenshots`, `both`, or unset)

```bash
npm run demo:screenshots
```

Regenerates all 8 files in `docs/assets/screenshots/`: `01-ehr-browser`,
`02-composition-pretty`, `03-composition-flat`, `03b-composition-json`,
`04-templates`, `05-servers`, `06-aql-runner`, `07-aql-autocomplete`.

Review each one before committing — `saveElementScreenshot()` in
`capture-screenshots.js` crops to the lowest real content element it can
find (to avoid empty space below a flex-stretched panel), which is a
heuristic, not pixel-perfect. Known cosmetic issue: the Composition
Viewer's Pretty tab shows `[object Object]` for a couple of composite RM
attributes (`composer`, `origin`, event `time`) — see the README's "Known
limitations" section before trying to "fix" this by chasing it as a bug.

## Step 2: Hero video + gif (if `$1` is `video`, `both`, or unset)

```bash
npm run demo:video
```

Records a ~35s walkthrough (add a server + test connection → EHR Browser →
Templates → AQL Runner with template-aware autocomplete), then encodes
`docs/assets/demo.mp4` (h264, supersampled capture at `deviceScaleFactor:2`
for sharp downscaled text), `docs/assets/demo.gif` (diff-based palette, no
dithering, gifsicle-optimized), and `docs/assets/demo.vtt` (captions timed
from the actual recorded scene durations, not hand-typed).

Re-running this will not byte-for-byte reproduce a previous recording —
real interaction timing has a second or so of natural jitter per scene.
That's expected; watch the result rather than diffing timestamps.

If you change the recorded script (add/remove/reorder scenes) in
`record-video.js`, update `docs/index.html`'s `<video aria-label>` and
`.preview-caption` text, and `README.md`'s gif `alt` text, to match — they
currently describe the "add server → EHR Browser → Templates → AQL Runner
autocomplete" flow.

## Step 3: Review and commit

1. Skim every regenerated screenshot and watch the mp4 (or open the gif) —
   this is marketing-facing content, worth an actual look, not just "the
   script exited 0."
2. `git diff --stat` to confirm only the expected `docs/assets/` files
   changed (plus `docs/index.html` / `README.md` if you updated captions
   per Step 2).
3. Commit with a message describing what changed and why (new flow, fixed
   a visual bug, updated fixture data, etc.) — not just "regenerate demo
   assets."
4. Do NOT push or open a PR unless the user explicitly asks.
